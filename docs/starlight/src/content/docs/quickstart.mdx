You will train a model to answer one question: **will a customer buy again
within 30 days?** One example is a customer at a particular point in time,
with the orders known then and a label describing what happened afterward.

## Run it

Download [repeat_purchase.py](/examples/repeat-purchase/repeat_purchase.py).
With [uv installed](https://docs.astral.sh/uv/getting-started/installation/), run:

```bash
uv run --no-project --python 3.12 --with relflow repeat_purchase.py
```

The script creates a small fictional dataset, trains on CPU, saves and reloads
the model, and prints a return probability for three new customers. Files are
written to `repeat-purchase-run/`. No text encoder or external dataset is needed.

The sample is a workflow exercise; its simulated behavior is not evidence of
retail prediction quality.
You can inspect a [recorded execution](/examples/repeat-purchase/recorded-run.json)
with the exact settings, file hashes, and returned probabilities.

## Describe the model

```python
import relflow as rf


class Order(rf.Branch):
    amount = rf.Number
    category = rf.Category
    days_ago = rf.Number


class Customer(rf.Model):
    days_since_signup = rf.Number
    orders = Order(length=32, overflow="tail")
    returns_in_30d = rf.Boolean(mask=True)


if __name__ == "__main__":
    model = Customer(preset="small")
```

The field types tell relflow how to represent the values. `Order` defines the
fields belonging to each event; placing it under `orders` makes a collection.
`mask=True` defines the answer to learn and excludes its value from the input.

Orders arrive oldest to newest. The branch keeps at most 32, retaining the
latest ones. Creating the class definitions allocates no network; constructing
`Customer(...)` creates a new, untrained model.

## Learn from the historical examples

The script writes training and validation Parquet files. These snippets follow
its operations. To try them interactively against the generated files, first
enter `repeat-purchase-run/` with `cd repeat-purchase-run`. Train from the nested
records directly:

```python
data = rf.ArrowDataModule(
    train="train.parquet",
    validate="validation.parquet",
    num_workers=0,
    pin_memory=False,
)
model.fit(
    data,
    batch_size=128,
    learning_rate=1e-3,
    max_epochs=6,
    accelerator="cpu",
    devices=1,
)
model.save("customer.rf")
```

Training learns field representations and relationships in the order history
for the return objective. You supply records with labels rather than a separate
table of engineered aggregates.

## Predict for new customers

Load the saved model and supply new records without the answer:

```python
import polars as pl

trained = rf.Model.load("customer.rf")
requests = pl.read_parquet("requests.parquet")
result = trained.predict(
    requests,
    retain=("customer_id",),
    batch_size=128,
)

for row in result.iter_rows(named=True):
    customer = row["inputs"]["customer_id"]
    probability = row["predictions"]["returns_in_30d"]["content"]["probability"]
    print(customer, probability)
```

The output is an eager Polars DataFrame. Each probability stays beside its retained
customer identifier. The script also saves the predictions and a run receipt,
so you can inspect your actual output.

The [recorded fictional run](/examples/repeat-purchase/recorded-run.json), made
with the [archived source](/examples/repeat-purchase/recorded-source.py), returned
these probabilities, rounded to four decimal places:

| Customer | Chance of another purchase within 30 days |
| --- | ---: |
| `recent` | 0.8004 |
| `less-recent` | 0.1236 |
| `occasional` | 0.8006 |

These historical predictions illustrate the sample's simulated behavior. They
remain tied to that archived script and recorded environment; they are not a new
measurement of the current source revision. Your run can vary with software and
hardware.
