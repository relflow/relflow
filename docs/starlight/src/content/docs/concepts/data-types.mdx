All input data for relflow models is represented as the leaf of a model tree. As mentioned under [Modular Modeling](/modular/), relflow defines a plug-in registry for each data leaf; this registry enforces fulfillment of a contract in which:

- Raw data, in its nominal state, is passed to the leaf
- A vector of standard dimensionality (as determined by the model’s initialization) is emitted by the leaf and passed along the leaf’s heritage path.

## State vs content

Every leaf promises to emit one vector per observation, an embedding which is learned to best represent the ingressed data. The standard relflow data leaves draw a distinction between two aspects of the observed data: state, and content.

The state of a data observation must be one of six distinct values, given in the below table:

| State | Meaning |
| --- | --- |
| <StateToken state="valued" /> | The data observed does exist, and is available for modeling purposes |
| <StateToken state="null" /> | The observation has no value for this field (`None`/null). |
| <StateToken state="padded" /> | No collection item exists at this position; padding aligns differently sized collections. |
| <StateToken state="masked" /> | The data observed does exist, but is intentionally hidden for model training / reconstruction |
| <StateToken state="other" /> | The data observed is not `None`, but it also is not of a usable value for modeling (this may be a `np.NaN` value for numerical representation, or a Vector with infinite values) |
| <StateToken state="hurdle" /> | The value equals a field's declared `hurdle`, such as an exact zero, and is modeled as a state rather than a quantity |

This state value is incorporated into the same embedding which a relflow leaf emits as the data observation’s representation. The decoder of each leaf, unless otherwise stated, will decode the learned embedding into

1. A discrete `state` value, penalized by cross-entropy
2. A representation of the original content, penalized with unique loss functions for each leaf.

## Leaf addresses

The heritage path of a data leaf describes where each leaf exists in relation to all, if any, parent branches. This heritage path is represented in a 1:1 manner with standard file-path addresses, where the root directory of a file-path represents a model object.

Critically, the default heritage path for a leaf is the assumed query path under which the leaf’s data exists, relative to the tensordict in which data is passed from a data loader (and optional pre-processor) into the model.
