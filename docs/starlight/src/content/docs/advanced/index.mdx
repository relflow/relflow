Relflow promises to abstract away the most complex aspects of deep learning
for enterprise data. However, we also know that it is sometimes necessary for
practitioners to open the hood of models as advanced as relflow and to fully
take advantage of the customizability offered.

Below, you will find details around advanced features and applications of
relflow models. If you have a unique challenge which you feel is not clearly
addressed here, please feel free to
[open a ticket](https://github.com/relflow/relflow/issues/new/choose),
or [reach out to our community on Discord](https://discord.gg/DVyZUkvTFA)!

## Keep the surrounding contract explicit

An extension fits into a larger workflow. Define the observation and its cutoff,
the information available at prediction time, and the outputs your application
expects. Preserve record boundaries and target alignment as data moves through
the pipeline.

| Change | Owning layer |
| --- | --- |
| Join, filter, rename, sort, or derive source values | `rf.Preprocessor`. |
| Select values already present in the prepared observation | The schema’s explicit node queries. |
| Deliver observations repeatedly for training and evaluation | A source factory or data module. |
| Represent a new kind of value and/or learn from it in a chosen manner | A tensorfield extension. |
| Choose a decision from a prediction | Application policy or an `rf.Postprocessor`. |

For example, grouping transactions into customer histories belongs to data
preparation. Choosing how a new signal is encoded and embedded belongs to its
field type. The [data flow guide](/concepts/data-flow/) explains how those
operations meet at the model schema.

## State is part of the model

A deployed model has parameters and field-owned state. Vocabulary order,
normalization statistics, and extension resources affect how source values are
represented. Reusing a schema does not by itself establish that two model
instances have the same learned state.

The [online vocabulary guide](/advanced/online-vocabulary/) follows one concrete
case: a new label can be admitted before the model has learned from it. The
[checkpoint guide](/advanced/checkpoints-and-state/) connects those changes
to model artifacts and full training resumption. The
[mutation guide](/advanced/mutations/) covers intentional schema edits and
the boundaries of compatible state retention.

## Separate the learning task from its downstream use

The [masking and pretraining guide](/advanced/masking-and-pretraining/) explains
how visible context and reconstruction targets define a learning task.
[Embeddings](/advanced/embeddings/) exposes learned context for a separate
downstream use. Evaluate the target task and that downstream use independently.

When you scale either workflow, coordinate the
[distributed data plan](/advanced/distributed-data/), saved model state, and
[inference contract](/advanced/inference-and-deployment/). Batch size, source
ownership, and output identity belong to that plan as well as the model’s schema.

## Follow the implementation boundary

The guides link to the source definitions and contract tests behind their
examples. The [API map](/api-map/) identifies the documented source revisions
and the public extension bases. The [Evidence library](/evidence/) provides
separately recorded learning experiments, with their original revisions and
protocols.

Start with the guide for the behavior you are extending, then test its contract
with nested records, missing values, repeated passes, and saved state appropriate
to that integration.
