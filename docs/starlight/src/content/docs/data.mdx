Before writing a schema, finish this sentence:

> Given what we know **at this moment**, predict **this outcome**.

For repeat purchases: given a customer's account details and order history at
the end of today, predict whether they buy again in the next 30 days.

## One example is one decision

One row in the training set represents one customer at one cutoff. The row
can contain several related records, including a list of orders. A customer
can appear at different cutoffs, but evaluation should reflect how that reuse
will happen in production.

| Part | In the purchase example |
| --- | --- |
| Decision unit | A customer at the end of a day. |
| Known information | Account age and orders placed by that cutoff. |
| Answer | Whether another purchase occurs in the next 30 days. |
| Production evaluation | Later cutoffs with complete outcome windows. |

Only use information available when a real prediction would be made. Exclude
future orders and fields updated after the outcome. Make sure the whole
30-day label window has elapsed before assigning a negative answer.

Each amount belongs to its own category and date. The model can learn from
those relationships across the history. You do not need to replace the history
with a single row of counts and averages before modeling it.

Data may begin in multiple database tables, Parquet files, or another source.
Your application assembles the intended observations and decides which records
belong together. The model schema describes the resulting structure.

## Put bounds on the history

```python
orders = Order(length=32, overflow="tail")
```

This placement keeps the latest 32 orders when the input is ordered oldest
to newest. A cap is a resource choice: longer context can expose more history
and use more memory. Compare useful history lengths on a held-out evaluation.

## Keep training answers out of requests

Training data contains the labels needed to learn. `mask=True` excludes those
values from the input and defines a supervised objective. Prediction requests
omit them entirely.

Identifiers used only for matching results to your application can be retained
without making them model inputs. For example, keep `customer_id` outside
the model schema and select it with `retain=("customer_id",)` when predicting.

## Evaluate the decision, including its costs

Choose a split that represents deployment. A time-based split is useful when
the task predicts later events. Take care with overlapping outcome windows
and repeated entities across splits.

Compare predictive quality against a sensible baseline and the cost of the
decisions made from the scores. A good ranking metric does not by itself
choose the threshold or establish calibrated probabilities.

The [model schemas](/concepts/models/) show how to describe these observations. The
[benchmarks](/benchmarks/) and [controlled experiments](/evidence/) show two
different kinds of supporting evidence.
